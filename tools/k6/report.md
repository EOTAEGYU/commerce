> **100명 동시 주문 상황에서 비관적 락이 재고를 정확히 50건으로 제한. 초과 판매 0건.**

주문 성공 응답 p(95) 575ms는 DB 행 잠금 대기 비용으로 로컬 환경에서 허용 범위.

## 시나리오 B — 배치 쿼리 개선 Before/After

### 테스트 조건

| 항목 | 값 |
|------|----|
| 대상 API | `GET /api/products?page=0&size=20` |
| VU 구성 | 0 → 50 (1분 증가) → 50 유지 (2분) → 0 (1분 감소) |
| 총 테스트 시간 | 4분 |
| SLO 목표 | p(95) < 200ms |

---

### 적용 전 — N+1 쿼리

**코드 구조**
```kotlin
// 상품마다 쿼리 2회씩 발생 (20개 상품 = 40회 + 목록 1회 = 총 41회)
return productPage.map { product ->
    val avg = reviewRepository.findAverageRatingByProductId(product.id)  // 상품당 1쿼리
    val cnt = reviewRepository.countByProductId(product.id)              // 상품당 1쿼리
    ProductResponse.from(product, avg, cnt)
}
```

**측정 결과**

| 지표 | 값 |
|------|----|
| 총 처리 요청 수 | 26,425회 |
| 처리량 | 110 req/s |
| 평균 응답시간 | 340.84ms |
| p(90) | 833.49ms |
| **p(95)** | **974.97ms** |
| 최대 | 3,850ms |
| **에러율** | **48.03%** (12,694건 실패) |

**에러 발생 원인**
```
50 VU 동시 요청
  → 상품 1페이지 조회 시 DB 쿼리 41회 발생
  → HikariCP 커넥션 풀 고갈
  → Connection timeout → 48% 요청 실패
```

### 적용 후 — 배치 쿼리

**코드 구조**
```kotlin
// 전체 상품 ID로 통계를 한 번에 조회 (총 2회)
val productIds = productPage.content.map { it.id }
val statsMap = reviewRepository.findStatsByProductIds(productIds)  // IN 쿼리 1회
    .associate { row -> ... }
return productPage.map { product ->
    ProductResponse.from(product, statsMap[product.id]?.first, ...)
}
```

### 적용 후 — 로컬 캐시 (Caffeine)

**코드 구조**
```kotlin
// ProductService.getList()

    cacheNames = ["products"],

@Transactional(readOnly = true)
fun getList(categoryId: Long?, keyword: String?, pageable: Pageable): Page<ProductResponse> { ... }
```

**캐시 설정 (application.yaml)**

### 결론

> **로컬 캐시(Caffeine, TTL 60s) 적용으로 p(95) 409ms → 44ms (▼89%), 처리량 148 → 2,047 req/s (+1,281%). SLO(p95 < 200ms) 달성.**

**트레이드오프 및 잔여 과제**

| 항목 | 내용 |
|------|------|
| 캐시 무효화 | `update()` / `delete()` 시 `@CacheEvict` 미적용 → TTL 60s 내 변경 미반영 |
| 다중 인스턴스 | 인스턴스 간 캐시 불일치 → 수평 확장 시 Redis로 전환 필요 |
| 캐시 미스 | 첫 요청 또는 TTL 만료 직후 DB 쿼리 2회 발생 (배치 쿼리 성능 동일) |
